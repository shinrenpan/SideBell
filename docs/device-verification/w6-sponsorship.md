# W6 支持開發者 實機驗證清單

> 對應 change：`add-sponsorship`
> 三個消耗性內購（`com.shinrenpan.sidebell.tip.small` / `…medium` / `…large`），可重複購買，**不解鎖任何功能**。

## 裝置與版本

| 角色 | 裝置 | OS 版本 |
|---|---|---|
| 照顧者端 | iPhone 15 Pro | |
| 患者端 | iPad mini 7 | |

## ⚠️ 開始之前

| # | 前置條件 | 怎麼確認 |
|---|---|---|
| 1 | 付費 App 協議**有效** | App Store Connect >「協議、稅務與銀行業務」。未生效時沙盒購買會失敗，而**錯誤訊息不會指出真正的原因** |
| 2 | 三個商品狀態為「準備提交」或更後續 | App Store Connect > App 內購買項目 |
| 3 | RevenueCat 主控台看得到三個商品 | 商品列表 |
| 4 | **Test Store 的 `test_` key 已填入** `Config/Secrets.xcconfig` | S1–S4、S6 用它就夠，不需要沙盒帳號 |
| 4a | Test Store **底下**看得到三個商品 | RevenueCat > Test Store app > Products。Test Store 與 App Store 的商品目錄各自獨立，App Store 側的商品**不會**自動出現在這裡；缺了它們，`test_` key 填對也載不到方案 |
| 4b | （**僅 S7 需要**）沙盒測試帳號已建立並登入 | `設定` > `App Store` > 沙盒帳號 |
| 5 | 前 1–3 項**只有 S7 需要**；S1–S6 不依賴 App Store Connect 的任何設定 | — |

> 📌 **「購買成功」一律以 App 內徽章出現為準**，不看收據內容。沙盒的收據與
> 正式環境不同，拿它當判準會得到不可重現的結論。

### 兩種測試環境的分工

| | Test Store（`test_` key） | 沙盒（`appl_` key ＋ 沙盒帳號） |
|---|---|---|
| 驗什麼 | **我們自己的判斷與接線**：取消、失敗、重複購買、無網路、徽章 | **App Store 那一側**：協議、上架地區、銀行資訊 |
| 購買流程 | SDK 自己彈的 alert，三個選項：購買／失敗／取消 | 真實的系統購買流程 |
| 前置 | 只要一把 key | 協議生效＋商品過審＋沙盒帳號 |
| 何時跑 | 平常（S1–S6） | **送審前一次**（S7） |

S1–S6 用 Test Store 跑，`test_` key 換上去即可；S7 換回 `appl_` key。

## S1. 入口只在照顧者端

- **對應**：`The support screen is reachable only from the caregiver side`

| # | 步驟 | 預期 | 實際 |
|---|---|---|---|
| 1.1 | 照顧者端 → `設定` 分頁 | 出現「支持開發者」一列，底下註明「支持不會解鎖任何東西」 | |
| 1.2 | 患者端 → 右上 `設定`（兩段確認）→ 逐項檢視 | **沒有**支持入口、沒有價格、沒有任何購買控制項 | |
| 1.3 | 患者端格子畫面 | 同上，全畫面無任何相關字樣 | |

## S2. 方案的呈現

- **對應**：`Each option states what the money is for`

| # | 步驟 | 預期 | 實際 |
|---|---|---|---|
| 2.1 | 照顧者端開啟支持頁（有網路） | 列出**三個**方案，由小到大 | |
| 2.2 | 檢視每一列 | 顯示**在地化價格**（台灣應為 NT$30 / NT$90 / NT$290）與該筆款項的用途說明 | |
| 2.3 | 檢視頁首 | 明白寫著「支持不會解鎖任何東西」 | |

> 價格若顯示為美元或空白，代表商品尚未在該地區上架，或 RevenueCat 未取得商品——
> 那是設定問題，不是程式問題。

## S3. 購買流程

- **對應**：`Supporting more than once`、`Cancelling is not an error`
- **前置**：已填入 Test Store 的 `test_` key（不需要沙盒帳號）

| # | 步驟 | 預期 | 實際 |
|---|---|---|---|
| 3.1 | 點選最小的方案，在 alert 選「購買」 | 回到頁面後**出現感謝** | |
| 3.2 | 回到 `設定` 分頁 | 「支持開發者」那一列出現愛心徽章 | |
| 3.3 | **再買一次同一個方案** | 不被阻擋，視為一筆新的獨立支持 | |
| 3.4 | 點選另外兩個方案各買一次 | 皆可完成 | |
| 3.5 | 點選任一方案後在 alert 選**取消** | **完全沒有錯誤訊息**，畫面靜靜回到原狀 | |
| 3.6 | 點選任一方案後在 alert 選**失敗** | 出現可讀的說明並可重試，**不出現 SDK 的錯誤碼** | |

> 3.5 是本片最容易做錯的一項。取消是使用者的決定，跳出錯誤訊息像是在責備他。

## S4. 無網路時的呈現

- **對應**：`The support screen states plainly when it needs a network`
- **前置**：開啟飛航模式（Wi-Fi 與行動網路都要斷）

| # | 步驟 | 預期 | 實際 |
|---|---|---|---|
| 4.1 | 開啟支持頁 | 明確說明「這個畫面需要網路連線」，並有**重試**按鈕 | |
| 4.2 | 檢視畫面 | **不是**空白清單、**不是**永遠轉不完的載入指示 | |
| 4.3 | 關閉飛航模式後按「重試」 | 三個方案出現 | |

## S5. 購買不改變任何功能

- **對應**：`Supporting the developer never changes what the app can do`
- **這是本片最重要的一項**。程式裡沒有任何依購買狀態決定功能的判斷，這裡驗的是那件事在實機上也成立。

| # | 步驟 | 預期 | 實際 |
|---|---|---|---|
| 5.1 | **購買前**：跑一次完整的呼叫閉環（患者按格 → 照顧者收到 → 確認 → 患者看到已確認） | 正常 | |
| 5.2 | 完成任一筆購買 | — | |
| 5.3 | **購買後**：再跑一次同樣的閉環 | 與 5.1 **完全相同**，沒有任何差異 | |
| 5.4 | 開啟飛航模式，再跑一次閉環 | 呼叫、警報、確認全部正常——它們走 BLE，不需要網路 | |
| 5.5 | 飛航模式下開啟 `設定` 分頁 | 徽章**仍然顯示**（旗標記在本機，不向伺服器查詢） | |

> 5.4 與 5.5 是這個設計的核心主張：離線是常態，而付過錢的人在離線時不該
> 看不到感謝。若徽章在飛航模式下消失，代表某處改成了向伺服器查詢。

## S6. 未設定 API key 時不崩潰

- **前置**：把 `Config/Secrets.xcconfig` 暫時改名（或把 key 改成 `appl_YOUR_KEY_HERE`），重新建置安裝

| # | 步驟 | 預期 | 實際 |
|---|---|---|---|
| 6.1 | 啟動 App | **正常啟動**，可進入任一角色 | |
| 6.2 | 跑一次呼叫閉環 | 完全正常 | |
| 6.3 | 開啟支持頁 | 顯示「需要網路連線」，**不崩潰** | |

> 測完把檔案改回來。這一項驗的是「金流設定缺失不該讓整個 App 起不來」——
> App 的核心是呼叫與警報，與金流毫無關係。

## S7. 送審前：真實 StoreKit 路徑

- **前置**：`Config/Secrets.xcconfig` 換回 `appl_` key；沙盒帳號已登入；付費 App 協議有效
- **這一組驗不到的東西，Test Store 也驗不到**——它是唯一會暴露 App Store 側設定問題的路徑

| # | 步驟 | 預期 | 實際 |
|---|---|---|---|
| 7.1 | 三個方案各以沙盒帳號購買一次 | 皆完成，App 內出現徽章 | |
| 7.2 | 檢視 RevenueCat 主控台 | 三筆交易都出現 | |

> 失敗時先查前置條件表的第 1–3 項。這條路徑的錯誤訊息**不會指出真正的原因**。

## 完成判準

- S1：患者端全無入口與價格
- S2：三個方案、在地化價格、用途說明皆正確
- S3：可重複購買；取消**不產生**錯誤訊息；失敗有可讀說明
- S4：無網路時說明清楚且可重試
- S5：購買前後行為完全相同；離線時閉環正常且徽章仍在
- S6：缺 API key 時 App 正常運作
- S7：送審前，沙盒的真實路徑三筆交易皆成立
