# W6 支持開發者 實機驗證清單

> 對應 change：`add-sponsorship`
> 三個消耗性內購（`com.shinrenpan.sidebell.tip.small` / `…medium` / `…large`），可重複購買，**不解鎖任何功能**。

|---|---|---|
| 照顧者端 | iPhone 15 Pro | |
| 患者端 | iPad mini 7 | |

## ⚠️ 開始之前

| # | 前置條件 | 怎麼確認 |
|---|---|---|
| 1 | 付費 App 協議**有效** | App Store Connect >「協議、稅務與銀行業務」。未生效時沙盒購買會失敗，而**錯誤訊息不會指出真正的原因** |
| 2 | 三個商品狀態為「準備提交」或更後續 | App Store Connect > App 內購買項目 |
| 3 | RevenueCat 主控台看得到三個商品 | 商品列表 |
| 4 | **Test Store 的 `test_` key 已填入** `Config/Secrets.xcconfig` | S1–S4、S6 用它就夠，不需要沙盒帳號 |
| 4a | Test Store **底下**看得到三個商品 | RevenueCat > Test Store app > Products。Test Store 與 App Store 的商品目錄各自獨立，App Store 側的商品**不會**自動出現在這裡；缺了它們，`test_` key 填對也載不到方案 |
| 4b | （**僅 S7 需要**）build 已上傳 TestFlight | 改走 TestFlight，用自己的 Apple ID 購買，不需要沙盒帳號（見 S7） |
| 5 | 前 1–3 項**只有 S7 需要**；S1–S6 不依賴 App Store Connect 的任何設定 | — |

> 📌 **「購買成功」一律以 App 內徽章出現為準**，不看收據內容。沙盒的收據與
> 正式環境不同，拿它當判準會得到不可重現的結論。

### 兩種測試環境的分工

| | Test Store（`test_` key） | 沙盒（`appl_` key ＋ 沙盒帳號） |
|---|---|---|
| 驗什麼 | **我們自己的判斷與接線**：取消、失敗、重複購買、無網路、徽章 | **App Store 那一側**：協議、上架地區、銀行資訊 |
| 購買流程 | SDK 自己彈的 alert，三個選項：購買／失敗／取消 | 真實的系統購買流程 |
| 前置 | 只要一把 key | 協議生效＋商品過審＋沙盒帳號 |
| 何時跑 | 平常（S1–S6） | **送審前一次**（S7） |

S1–S6 用 Test Store 跑，`test_` key 換上去即可；S7 換回 `appl_` key。

## S3. 購買流程

- **對應**：`Supporting more than once`、`Cancelling is not an error`
- **前置**：已填入 Test Store 的 `test_` key（不需要沙盒帳號）

| # | 步驟 | 預期 | 實際 |
|---|---|---|---|
| 3.1 | 點選最小的方案，在 alert 選「購買」 | 回到頁面後**出現感謝** | ✅ 2026-08-13 iPhone |
| 3.2 | 回到 `設定` 分頁 | 「支持開發者」那一列出現愛心徽章 | ✅ 2026-08-13 iPhone |
| 3.3 | **再買一次同一個方案** | 不被阻擋，視為一筆新的獨立支持 | ✅ 2026-08-13 iPhone：已買過的 `tip.small` 再點，alert 照常出現，無「已擁有」阻擋 |
| 3.4 | 三個方案各買一次 | 皆可完成 | ✅ 2026-08-13 iPhone |
| 3.5 | 點選任一方案後在 alert 選**取消** | **完全沒有錯誤訊息**，畫面靜靜回到原狀 | ✅ 2026-08-13 iPhone：無任何 UI 變化 |
| 3.6 | 點選任一方案後在 alert 選**失敗** | 出現可讀的說明並可重試，**不出現 SDK 的錯誤碼** | ✅ 2026-08-13 iPhone：底部橫幅「購買未完成，請再試一次。」可關閉，無錯誤碼 |

> 3.5 是本片最容易做錯的一項。取消是使用者的決定，跳出錯誤訊息像是在責備他。

> 💡 Test Store 的 alert 會列出 `Product ID`、`Title` 與 `Price`——那是**商店實際收到的
> 識別碼**，比對它與 `SponsorshipProduct` 的 rawValue 是驗識別碼最快的方法。
> 2026-08-13 的識別碼落差（少了 bundle ID 前綴）若早一步走到這裡就會現形。

## S4. 無網路時的呈現

- **對應**：`The support screen states plainly when it needs a network`
- **前置**：開啟飛航模式（Wi-Fi 與行動網路都要斷），**並且完全結束 App 再重開**

> ⚠️ 只開飛航、從上一頁重新進入支持頁**驗不到這一項**。RevenueCat 把商品資訊
> 快取在記憶體裡，離線時 `products()` 照樣回得出三個商品，因此載入是**成功**的，
> 畫面會照常列出方案——那不是 bug：spec 要求的是「無法連到商店時說清楚」，
> 而此時它連得到（快取）。離線仍看得到價格、購買失敗時才給可讀訊息，
> 比一片「需要網路」更好。要清掉記憶體快取只能結束進程（上滑關掉 App）。

| # | 步驟 | 預期 | 實際 |
|---|---|---|---|
| 4.1 | 飛航模式下**完全結束 App 再重開**，開啟支持頁 | 明確說明「這個畫面需要網路連線」，並有**重試**按鈕 | ✅ 2026-08-13 iPhone |
| 4.2 | 檢視畫面 | **不是**空白清單、**不是**永遠轉不完的載入指示 | ✅ 2026-08-13 iPhone：另附「呼叫與警報不受影響」的說明 |
| 4.3 | 關閉飛航模式後按「重試」 | 三個方案出現 | ✅ 2026-08-13 iPhone |
| 4.4 | （已驗）飛航下**不**結束 App，從上一頁重新進入支持頁 | 方案照常顯示（快取命中），**這是預期行為** | ✅ 2026-08-13 iPhone |

## S5. 購買不改變任何功能

- **對應**：`Supporting the developer never changes what the app can do`
- **這是本片最重要的一項**。程式裡沒有任何依購買狀態決定功能的判斷，這裡驗的是那件事在實機上也成立。

| # | 步驟 | 預期 | 實際 |
|---|---|---|---|
| 5.1 | **購買前**：跑一次完整的呼叫閉環（患者按格 → 照顧者收到 → 確認 → 患者看到已確認） | 正常 | ✅ 2026-08-13 iPhone＋iPad |
| 5.2 | 完成任一筆購買 | — | ✅ 2026-08-13 |
| 5.3 | **購買後**：再跑一次同樣的閉環 | 與 5.1 **完全相同**，沒有任何差異 | ✅ 2026-08-13 iPhone＋iPad：無任何差異 |
| 5.4 | 開啟飛航模式，再跑一次閉環 | 呼叫、警報、確認全部正常——它們走 BLE，不需要網路 | ✅ 2026-08-13 iPhone＋iPad |
| 5.5 | 飛航模式下開啟 `設定` 分頁 | 徽章**仍然顯示**（旗標記在本機，不向伺服器查詢） | ✅ 2026-08-13 iPhone：飛航＋重開 App 後，支持頁的感謝卡片仍在 |

> 5.4 與 5.5 是這個設計的核心主張：離線是常態，而付過錢的人在離線時不該
> 看不到感謝。若徽章在飛航模式下消失，代表某處改成了向伺服器查詢。

## S6. 未設定 API key 時不崩潰

- **前置**：把 `Config/Secrets.xcconfig` 暫時改名（或把 key 改成 `appl_YOUR_KEY_HERE`），重新建置安裝

| # | 步驟 | 預期 | 實際 |
|---|---|---|---|
| 6.1 | 啟動 App | **正常啟動**，可進入任一角色 | ✅ 2026-08-13 iPhone |
| 6.2 | 跑一次呼叫閉環 | 完全正常 | ✅ 2026-08-13 iPhone |
| 6.3 | 開啟支持頁（**網路正常，不要開飛航**） | **不崩潰**，且畫面有明確說明與重試，不是空白或無限載入 | ✅ 2026-08-13 iPhone：出現「需要網路連線」的說明與重試，未崩潰（文案不精確，見下註） |

> 6.3 此時顯示的文案會是「這個畫面需要網路連線」——網路其實是好的，那句話
> 對這個情境並不精確。`SponsorshipError.unavailable` 刻意把「連不到商店」與
> 「SDK 未設定」壓成同一種狀態，因為**缺 key 只可能發生在開發者自己的 build**
> （key 於建置時注入），正式版沒有這條路徑；真正的原因由 `configure()` 記在
> log 裡。因此本項的判準是**不崩潰**，不是那句文案。網路要保持正常，否則
> 分不清畫面是缺 key 造成還是斷網造成。

> 測完把檔案改回來。這一項驗的是「金流設定缺失不該讓整個 App 起不來」——
> App 的核心是呼叫與警報，與金流毫無關係。

## S7. 送審前：真實 StoreKit 路徑

- **前置**：`Config/Secrets.xcconfig` 換回 `appl_` key（已於 2026-08-14 換上）
- **這一組驗不到的東西，Test Store 也驗不到**——它是唯一會暴露 App Store 側設定問題的路徑

### 前置條件的三項，已於 2026-08-14 間接驗證通過

換上 `appl_` key 後，支持頁**列得出三個方案且帶價格**。程式碼在 `loadPlans()`
拿不到商品時直接 throw，沒有任何 fallback 文案或價格，因此「列得出來」這件事
本身就證明了商品確實從 App Store 取得。這一次取得同時證明了：

- 付費 App 協議**有效**（未生效時 `products()` 回空陣列）
- 三個商品在 ASC 的狀態**可用**（缺中繼資料時同樣回空）
- 三個識別碼**逐字正確**（三個全取到，不是只取到一部分）

也就是說，S7 存在的理由——那些「只有真實路徑才會現形」的 App Store 側設定
問題——已經現形過並通過。**剩下未驗的只有下表三項**。

### 改走 TestFlight

原訂用沙盒帳號跑，實際卡在沙盒帳號的雙重認證。改用 TestFlight：它同樣走
真實的 App Store 路徑，但用測試者自己的 Apple ID，不需要沙盒帳號。

送審前本來就要上傳 build，兩件事併作一趟。

| | Xcode build ＋ 沙盒帳號 | TestFlight |
|---|---|---|
| 帳號 | ASC 建立的沙盒帳號 | 測試者的真實 Apple ID |
| 卡點 | 沙盒帳號的雙重認證 | 無 |

| # | 步驟 | 預期 | 實際 |
|---|---|---|---|
| 7.1 | 上傳 build 至 TestFlight，三個方案各購買一次 | 皆完成，App 內出現徽章 | ✅ 2026-08-14 iPhone：三筆皆完成，購買 sheet 標明「僅供測試使用，不會導致扣款」，徽章「謝謝你的支持」出現 |
| 7.2 | 檢視 RevenueCat 主控台 | 三筆交易都出現 | ✅ 2026-08-14：Customers → Sandbox → 該 customer 的 Customer history 列出三筆，**幣別記為 TWD 30／90／290** |
| 7.3 | 檢視方案的名稱、說明與價格 | 名稱與說明為 ASC 的繁中本地化；價格為 App Store 提供的在地化字串 | ✅ 2026-08-14 iPhone：名稱與說明皆為 ASC 繁中；價格顯示 `$30.00`／`$90.00`／`$290.00`（見下註） |

> ⚠️ **7.1 之前務必先刪掉 App**。先前的測試已把「曾經支持過」的旗標寫進本機，
> 徽章會是亮的——不刪掉重裝，「購買後出現徽章」這個判準等於沒驗到。

> **7.3 的價格格式：`$30.00` 是最終答案，不是缺陷。** S2.2 原本推測美元符號是
> Test Store 的特性，真實路徑會變成 `NT$30`——**那個推測錯了**，正式 StoreKit
> 路徑顯示的同樣是 `$30.00`。
>
> 追下去的結果：`localizedPriceString` 在 StoreKit 2 底下就是
> `SK2Product.displayPrice`，也就是 **Apple 直接輸出的字串**。RevenueCat 自建的
> 那個 formatter 只服務另一個 `priceFormatter` 屬性，與這條路徑無關。
>
> 因此**沒有東西可以修**。要顯示 `NT$` 只能自行拼接貨幣符號，而那正是
> `SponsorshipPlan.displayPrice` 註解要避免的事：自己拼的數字遲早會與使用者
> 實際被扣的金額不一致。金額正確、來源權威，到此為止。
>
> 7.2 的交易記錄替這個結論補上最後一塊：**RevenueCat 收到的幣別是 TWD**
> （30／90／290）。金流那側完全正確，差異只在顯示字串的符號寫法。

> 7.2 若沒有交易，先查這個專案的 `app_store_connect_api_key_configured` 為
> `false`——收據驗證靠的是已設定的 In-App Purchase Key，理論上不受影響，但那是
> 第一個該查的點，其次才是協議與商品狀態。
