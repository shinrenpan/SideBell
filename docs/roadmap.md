## v1.1（目標 2026/10）

### Remote Push 互補通道

- **定位**：BLE 為主（同一空間、零網路依賴），push 補「照顧者短暫外出」的場景。
  **是互補，不是替代**——離線可用仍是這個產品的核心主張。
- **技術路線**：CloudKit ＋ `CKQuerySubscription`。患者端寫入呼叫紀錄，
  照顧者端經 APNs 收推播，**免自建 server**。
- **前置已備妥**：`CallTransport` 抽象層就是為此預留的插槽，1.0 不含任何
  CloudKit 程式碼。

#### 只做同帳號（private database）

原本規劃的是 CloudKit **共享**資料庫（`CKShare`），而那正是把這件事推遲到
1.1 的主因：建立 share、產生邀請、對方接受、處理過期與拒絕——每一種失敗都要
有對應的 UI，而使用者是長輩與看護。

改用**同一個 iCloud 帳號的 private database** 之後，那整塊工程消失：兩台裝置
登入同一個 Apple ID 就結束，subscription 直接掛在 private DB 上。

這涵蓋「家人照顧家人」——長輩的 iPad 本來就常是子女設定的，同帳號是現況而非
妥協。

**先做這個版本的真正理由，是它能用最小成本回答最大的未知數：推播到底夠不夠
即時。** APNs 的 silent push 有節流，系統會依電量與使用習慣調整送達時機。若
實測是分鐘級延遲，整個 Remote Push 的定位就得改寫——從「外出時的通道」變成
「事後補一則通知」，而 UI 上必須誠實標示它與藍牙那條的即時性不同。

跨帳號做得再完整，也回答不了這個問題。

#### 實作時要記得的兩件事

- **推播會送到該帳號的所有裝置**，包括患者自己的 iPad。要依角色過濾，否則第一
  次測試就會看到「患者按了自己的平板跳通知」。
- **警報邏輯得分岔**：推播的延遲與折疊語意與 BLE 不同，不能共用同一套判斷。

### App 內指向使用教學的入口

線上教學（中英雙語）已上線於 `shinrenpan.github.io/SideBell/guide/`，但目前
**App 裡沒有任何地方連得到它**。

商店描述裡的網址在 App Store 上不可點擊，能點的只有產品頁的 Support URL 與
Marketing URL——那些是使用者**下載之前**才會經過的位置。真正需要教學的時刻是
下載之後、對著兩台裝置不知道下一步的時候。

**最合適的位置是首次啟動的免責畫面**：每個使用者都必經，而且正好落在最困惑的
那一刻。加一行連結即可，不需要 in-app browser。

順帶補上 1.0 未竟的 onboarding 需求（見 `DECISIONS.md` 引導使用模式那條）：
「開啟引導使用模式」「不要滑掉 App」「床邊那台接著電源」三件事**教學已經寫了**，
但 App 內完全沒提。有了這個入口，那三件事就有地方可去。

### 中文用詞：「患者」改為「病友」⚠️ 教學已改，App 未改

一位病友建議把「患者」改成「病友」。**這是第一個來自實際使用者社群的用詞
回饋**，比開發者的語感可靠——`病友` 在台灣的病友團體裡是通行的自稱與互稱，
`患者` 則是臨床視角的第三人稱。

**線上教學（中文版）已全數改用「病友」，包括角色名稱「病友端」。**

**App 的 15 條 zh-Hant 字串還沒改**，所以在下次送審之前，教學寫「病友端」而
按鈕上是「患者端」。這是已知且刻意接受的暫時落差——用詞的正確性優先，而
落差會在下一版消失。

要改的字串（`Sources/Resources/Localizable.xcstrings`，只動 zh-Hant）：

```
患者端 / 架設在患者身邊，用來發出呼叫 / 隨身攜帶，接收患者的呼叫
你想讓患者能夠表達什麼？ / 患者將無法再用這一項求助。
送出確認，患者會看到有人回應了 / 患者按下格子後，呼叫會出現在這裡。
已超過三分鐘，患者端已顯示無人回應 / 目前收得到患者的呼叫
目前收不到患者的呼叫，患者不在範圍內 / 這個項目不能刪除，它是患者求助的方式。
離開目前角色並回到首頁，可重新選擇患者端或照顧者端
確認未送達——目前連不上患者的裝置，請靠近一點再試一次
這個畫面放得下 %lld 項。再多患者就看不到了——請先刪掉一項。
項目越多，患者尋找想按的那一格就越費力。（後略）
```

**英文維持 `Patient`**：`病友` 沒有自然的英文對應詞，`fellow patient` 在
介面上不成立。這是 zh-Hant 專屬的用詞調整。

改完之後，中文教學裡 21 處「病友端」的截圖也要重拍——那是**畫面上的字**，
不是散文。見 `docs/guide-screenshots.md`。

### 印尼語、越南語

台灣居家照護現場，外籍看護常常是**照顧者端的主要操作者**。本地化成本低、
實際價值高——這不是市場擴張，是讓真正在按那支手機的人看得懂。

字串架構在 W5（`add-localization`）就已預留，加語言不需要改程式碼。

## 待評估（無時程）

### Remote Push 的跨帳號模式（CKShare）

v1.1 只做同帳號。跨帳號是為外籍看護規劃的，前提是「他們不會使用雇主的
Apple ID」——這個推論合理，但**目前是假設，還沒有任何一位實際使用者證實過**。
也可能真實情況是雇主本來就提供工作機並設好帳號。

推廣通路（協會、輔具中心、居服督導）本來就會帶回這個答案。**先接觸到人，再
決定要不要做這塊工程。**

若確定要做，優先考慮**自動判斷而非讓使用者選**：BLE 配對時交換一個帳號識別的
hash，由程式決定走哪條路。

理由是「不需要帳號、不需要設定」正是這個 App 現在最強的地方之一——商店描述
第一段就寫著 *No account, no sign-up, no internet*。加一個模式選擇，等於要
使用者在開始用之前先回答一個他答不出來的問題（「你們是同一個 Apple ID 嗎？」）。

### 多患者：一位照顧者對多位患者

一 Central 連多 Peripheral。機構或多床家庭會需要。

**現況**：`ConnectionState.connected(peerCount:)` 已經帶對端數量而非布林值，
資料結構不必改；1.0 的 UI 只呈現一位患者。

> 多**照顧者**（一 Peripheral 對多 Central，輪班情境）**已經支援**：任一人
> 確認即全體閉環。這與多患者是不同的方向，不要混淆。

### 多照顧者：Ack 沒有回推給其他人 ⚠️ 已確認的落差

**這不是待評估，是規格寫了但沒實作。**

開發前的規格寫著：

> 多照顧者：一 Peripheral 可被多 Central 同時連線訂閱，天然支援輪班；
> 任一人 Ack 即全體閉環（**Ack 經 notify 回推全體**）。

括號裡那句沒有被實作。實際的 GATT 定義是：

```
callMessageUUID  properties: [.notify]   患者 → 照顧者
ackUUID          properties: [.write]    照顧者 → 患者，單向
```

`ackUUID` 只有 `.write`，患者端收到確認後沒有任何通道能把這件事廣播回去。
`ackReceived` 事件的兩個消費者（`CallCenter`、`CallDelivery`）也都在患者側。

**後果**：輪班時兩位照顧者同時連著，A 按下確認後患者端正確顯示「已確認」，
但 **B 的手機會繼續響**，直到三分鐘逾時或 B 自己也按一次。

不會漏接呼叫，但「已經有人處理了還一直響」這種體驗，久了會讓人乾脆把警報
關掉——那才是真正的風險。

**修法**（三處，需雙裝置驗證）：

1. `ackUUID` 加上 `.notify`
2. 患者端收到 ack 後 `updateValue(...)` 廣播給所有訂閱的 central
3. 照顧者端訂閱 ack characteristic，收到就停掉對應的警報

**為什麼驗證沒抓到**：W1–W7 的實機清單全部是一對一，從來沒有三台裝置同時
連線的項目。已於 `w4-caregiver-alerts.md` 補上 C9，標為未執行。

### 重送／Ack 狀態機的其餘邊界

多人**同時**按下確認的競態尚未窮舉——同一個 `callID` 被確認兩次看起來無害，
但沒有測過。修好上面那條之後一併處理。

### Android 照顧者端

照護家庭的 Android 佔比高。但 BLE 廣播的 overflow area 限制在 Android 上
表現不同，需要先評估可行性再談。

## 推廣（非開發）

目標族群不逛 App Store，得主動觸及：

- 漸凍人協會
- 各縣市輔具資源中心
- 醫院職能治療師（OT）
- 居服督導體系

目的是雙重的：觸及真實需求的家庭，同時取得**真實患者的實測回饋**——眼控精度、
格子詞彙是否貼合實際需要，這些只有真的在用的人說得準。
