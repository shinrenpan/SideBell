## Context

SideBell 目前只有需求文件與決策紀錄，沒有可執行程式。本 change 要立起專案骨架與傳輸層，並在兩台實機上把「背景 BLE 到底行不行」這個問題從假設變成事實。

三個既有約束框住了本設計：

1. **State Restoration 決定了啟動時序。** 系統因記憶體壓力終止 App 後，要靠 BLE 事件把 App 在背景喚醒；Core Bluetooth 要求 manager 在 App 啟動的最早期回呼中就重建，否則系統無從交還已恢復的狀態。這直接排除了 SwiftUI 應用程式生命週期，也決定了角色設定不能存在需要先載入的資料庫裡。
2. **背景喚醒時沒有 UI。** App 被 BLE 事件喚醒時，畫面與 ViewModel 都不存在，因此消費傳輸事件的角色不能是任何 ViewModel——必須是一個與 App 同壽命的物件。
3. **驗證環境不完整。** 開發機為 iPad mini 7（iOS 27 beta，患者端）與 iPhone 15 Pro（iOS 26，照顧者端）。deployment target 為 iOS 18.0，但 iOS 18 至 25 之間沒有任何實機可驗。

## Goals / Non-Goals

**Goals:**

- 建立可重現的建置流程：從乾淨 checkout 到可安裝 App，不需要任何手動 Xcode 設定。
- 定出 `call-transport` 的契約形狀，讓後續里程碑的呼叫、警報、紀錄邏輯完全不接觸 Core Bluetooth。
- 用測試釘死 `call-wire-format` 的編解碼與畸形輸入防禦，這是唯一能在無實機情況下獲得確定性的部分。
- 讓最小可運作的雙向路徑（患者送出、照顧者收到、照顧者確認、患者看到確認）在兩台實機上跑通，涵蓋鎖屏、離開範圍、系統終止三種情境。
- 產出一份可執行的實機驗證清單，明確標註每項結果取自哪個 OS 版本。

**Non-Goals:**

- 任何業務畫面（患者格子、格子編輯、照顧者儀表板、歷史紀錄、設定、贊助）。
- 任何 SwiftData 資料模型；角色設定以輕量儲存實作，不走資料庫。
- 警報播放、語音播報、本地通知；PoC 收到呼叫時只更新畫面文字。
- 未確認呼叫的重送與逾時狀態機；本 change 只走單次送達路徑。
- 多患者的介面呈現；傳輸層以集合管理連線，但畫面只呈現一個對象。
- 使用者手動滑掉 App 後的復活——iOS 不提供此能力，屬平台限制。

## Decisions

### 以 xcodegen 從 project.yml 生成 Xcode 專案

Info.plist 的背景模式、藍牙用途說明、capabilities 都是本專案最容易「被誤改而無聲失效」的設定：改錯不會編譯失敗，只會在某次鎖屏測試時神秘地收不到呼叫。放進純文字 manifest 後，這些設定在 code review 與 git 歷史上都看得見。

替代方案是直接維護 xcodeproj。否決原因不是美學，是 pbxproj 的 diff 幾乎不可讀，而本專案恰好把命脈押在少數幾個 plist 鍵值上。

Info.plist 以獨立檔案維護並由 manifest 指向，而非內嵌在 manifest 裡，讓 plist 保持標準格式、可被工具直接檢視。

### 進入點採 AppDelegate + SceneDelegate，並在啟動回呼建立傳輸層

App 啟動回呼負責三件事，順序固定：讀取角色設定、建立傳輸層、建立事件消費者。三者都必須在任何場景啟動之前完成，因為系統可能在完全沒有場景的情況下把 App 喚醒。

SceneDelegate 只負責視窗與導航裝配，不碰傳輸層。視窗根為導航控制器，並設定不透明背景色。

替代方案是 SwiftUI 應用程式生命週期加上啟動時的 task。否決原因是該生命週期不保證在系統交還已恢復狀態之前完成 manager 重建，而這正是背景復活能否成立的關鍵。

### CallTransport 契約以角色啟動、送出、確認、事件流四項為界

契約只暴露四個概念：以角色啟動、送出一則呼叫、確認一則呼叫、觀察事件與連線狀態。事件流涵蓋收到呼叫、收到確認、連線狀態變化三類。

事件以非同步序列傳遞而非委派協定，理由是消費端只有一個且需要跨越 App 生命週期；委派會誘使多方註冊，而多方註冊在背景喚醒情境下會產生「誰負責處理」的模糊地帶。

送出與確認為可拋出的非同步操作，失敗以具名錯誤回報（未連線、編碼失敗、寫入被拒），不得以布林值或靜默忽略表達失敗——靜默失敗是本產品最致命的缺陷類型。

### 事件序列採無上限緩衝，並在啟動回呼即接上消費者

App 被 BLE 事件喚醒時，事件可能早於任何消費者出現。若事件序列使用會丟棄元素的緩衝策略，這則呼叫就永遠消失，而症狀是「偶爾收不到」——最難追的失敗模式。因此事件序列採無上限緩衝，且消費者在啟動回呼中就建立，不等場景啟動。

非同步序列只能被迭代一次，這帶來一條不可違反的約束：**消費者的壽命與 App 相同，停止傳輸時不得停止消費**。一旦取消消費工作，該序列即永久終止，之後重新啟動傳輸所接到的是一條死掉的序列，事件永遠送不進來。此處的實際症狀是「切換角色後再也連不上，重開 App 才正常」——W1 實作期間已踩過一次，並以 CallCenter 的生命週期測試釘住。因此停止傳輸只停止底層端點與重設連線狀態，消費工作留到物件銷毀時才結束。

### 引入 CallCenter 作為 App 生命週期的事件消費者

傳輸事件的消費者是一個與 App 同壽命的物件，本 change 稱為 CallCenter，位於核心層並標注主動作者隔離。它在啟動回呼建立，持有傳輸層、消費事件序列、維護目前連線狀態與最近收到的呼叫。ViewModel 觀察 CallCenter，而非直接持有傳輸層。

本 change 只實作 CallCenter 的最小形式：持有、消費、暴露狀態。警報、紀錄寫入、重送狀態機都是後續 change 掛在同一個位置上的職責。

替代方案是讓 ViewModel 直接消費傳輸事件。否決原因是 ViewModel 生命週期綁在畫面上，背景喚醒時它不存在，等於呼叫沒有人接。

### 傳輸層整體採主動作者隔離，Bluetooth 回呼走主佇列

`BLETransport` 與其內部的 Peripheral、Central 端點都標注主動作者隔離，Bluetooth manager 以主佇列建立。

理由是事件率極低——本產品一天的呼叫數量以個位數計，單則訊息上限 131 位元組，沒有任何重運算或大量 I/O。在這個負載下另開佇列只會換來跨隔離邊界的複雜度，而背景喚醒的除錯難度已經夠高了。這是一個明確以「可除錯性優先於理論上的並行度」為理由的取捨，不是預設值的懶惰套用。

編解碼為純函式，不接觸任何隔離狀態，因此標注為非隔離，可從任何情境直接呼叫。

### BLETransport 內部依角色拆為兩個端點，對外仍是單一實作

`BLETransport` 對外是唯一的傳輸實作，內部依角色委派給 Peripheral 端點或 Central 端點。兩個端點不同時存在：以患者角色啟動只建立 Peripheral 端點，以照顧者角色啟動只建立 Central 端點。

這樣拆的理由是兩端的委派協定、狀態機與失敗模式完全不同，混在一個型別裡會產生大量「這個回呼在哪個角色下才有意義」的條件判斷。拆開後每個端點的狀態機都可以獨立閱讀。

對外不暴露這個拆分，因為核心邏輯不該知道角色與 BLE 拓樸的對應關係。

### GATT 定義集中於單一檔案，服務識別碼一次產生後固定

服務與三個特徵的識別碼由 uuidgen 產生一次後寫死在單一檔案，連同特徵屬性與權限一併定義。三個特徵為：呼叫訊息（通知）、確認（寫入）、裝置資訊（讀取）。全部宣告為需要加密。

集中的理由是這些常數一旦與已安裝的 App 不一致就會導致連不上，而症狀看起來像「藍牙壞了」。集中在一處讓兩端不可能各寫各的。

### 照顧者端掃描一律以服務識別碼過濾

背景掃描必須指定服務識別碼，這是平台規則而非最佳實務。前景掃描也採同一路徑，避免出現「前景能連、背景連不上」這種只在特定情境浮現的分歧。

### 斷線後立即重新發出連線請求，不自行輪詢

在斷線回呼中立即再次發出連線請求。iOS 的連線請求沒有逾時，系統會保留這個意圖，裝置回到範圍內時自動完成連線。

替代方案是自行排程重試。否決原因是那會在背景消耗喚醒配額，且與系統既有的連線意圖機制重複。

### 角色設定存於輕量鍵值儲存

角色需要在啟動回呼中同步讀取，此時資料庫尚未載入。以鍵值儲存實作，值域為患者、照顧者、未選擇三種。

### PoC 畫面遵循既有分層慣例，但明確標記為丟棄式

PoC 畫面依專案既有的分層慣例建立，位於獨立的功能目錄下，以便後續里程碑整個目錄刪除而不留殘跡。畫面只有兩個動作與三項顯示：送出一則固定內容的呼叫、確認收到的呼叫；顯示連線狀態、最近收到的呼叫、最近收到的確認。

不建立獨立 target。理由是背景行為由 target 的背景模式與 capabilities 決定，在另一個 target 驗到的結論不保證在主 App 成立——而本 change 的全部價值就在於那個結論的可信度。

### 實機驗證清單以獨立文件交付並標註 OS 版本

驗證清單為版控中的獨立文件，每個項目包含前置條件、操作步驟、預期結果、實際結果與取得結果的 OS 版本欄位。背景喚醒與系統終止復活兩類項目，若結果取自 beta 裝置，須在正式版裝置複驗後才採信。

## Implementation Contract

**行為**：安裝在兩台實機上的 App，選擇角色後即自動連線；患者端按下送出後，照顧者端即使處於鎖屏背景狀態也會在畫面上顯示該則呼叫；照顧者端按下確認後，患者端畫面顯示該則呼叫已被確認。過程中不需要任何裝置選擇介面，僅需在首次連線時通過系統配對提示。

**介面形狀**：

- 傳輸契約提供以角色啟動、送出呼叫、確認呼叫三項操作，以及一個事件序列與一個連線狀態查詢。送出與確認為可拋出的非同步操作。
- 事件序列的元素涵蓋三類：收到呼叫（攜帶呼叫內容與來源裝置名稱）、收到確認（攜帶呼叫識別碼）、連線狀態變化。
- 呼叫訊息為值型別，欄位為識別碼、緊急旗標、指令代碼、標題、時間戳。
- 編解碼以純函式提供編碼與解碼兩個方向，解碼回傳可拋出的結果。

**失敗模式**：

- 未連線時送出：拋出未連線錯誤，呼叫端可觀察，不得靜默丟棄。
- 標題超出長度上限：在編碼前即拒絕並拋出錯誤，不得截斷後送出。
- 收到畸形封包：記錄後丟棄，不得崩潰、不得中斷連線、不得將部分解析結果當作有效呼叫。
- 收到未知呼叫識別碼的確認：靜默丟棄，此為刻意的靜默行為，因為多照顧者情境下重複確認屬正常現象。
- 未通過配對的裝置嘗試訂閱：由系統在 GATT 層拒絕，App 不需額外處理，但須在驗證清單中確認確實被拒。

**驗收標準**：

- 編解碼測試涵蓋 `call-wire-format` 中列出的全部 round-trip 案例與全部拒絕案例，且在無實機環境下可執行。
- 建置驗收：乾淨 checkout 執行專案生成後直接建置成功，無手動 Xcode 設定步驟。
- 靜態驗收：傳輸模組以外的原始檔皆未引入 Core Bluetooth。
- 實機驗收：驗證清單中的鎖屏三十分鐘送達、離開範圍後自動重連、系統終止後由呼叫喚醒三項皆通過，且每項標註 OS 版本。

**範圍界線**：

- 範圍內：專案生成設定、UIKit 進入點、角色儲存、傳輸契約與其 BLE 實作、編解碼與其測試、CallCenter 最小形式、丟棄式 PoC 畫面、實機驗證清單。
- 範圍外：警報與語音、本地通知、資料庫模型、重送與逾時、業務畫面、贊助與購買、多患者介面、CloudKit 相關的任何程式碼。

## Risks / Trade-offs

- **患者端測試機跑在 iOS 27 beta 上** → 背景 BLE 是每年最可能被調整、且 beta 期間行為最不穩定的區域。在 beta 上看到的異常先假設為 beta 問題，不得據以修改架構；背景喚醒與系統終止復活兩類結果須於正式版裝置複驗。
- **iOS 18 至 25 無實機可驗** → 這段區間的行為由「Core Bluetooth 近年未大幅變動」的推論背書，而非驗證。若上架後收到該區間的災情回報，優先考慮提高 deployment target 而非盲目臆測修法。
- **背景喚醒處理窗約十秒** → 本 change 的處理內容極輕（解碼加更新狀態），十秒綽綽有餘；但後續掛上警報與資料庫寫入後，這個預算會迅速吃緊。CallCenter 的處理路徑須維持在「同步、無等待」的形狀。
- **需要加密導致首次配對多一步** → 對眼控使用者而言，系統配對提示是無法用眼控完成的操作，須由照顧者在設定階段代為完成。此限制須寫入後續的引導流程需求。
- **患者端進背景後服務識別碼移入 overflow 區** → 僅明確指定該識別碼掃描的 iOS 中央裝置可見。本專案兩端皆為 iOS 且皆以識別碼過濾，因此成立；但這使得未來的 Android 照顧者端在此路徑上幾乎不可行，屬已知且已接受的限制。
- **事件序列採無上限緩衝** → 理論上若消費者長期停滯會累積記憶體。以本產品的事件率（一天個位數）此風險可忽略，且消費者在啟動回呼即建立，不存在長期無人消費的情境。
- **PoC 畫面留在主 App 內** → 有被遺忘而隨正式版一起上架的風險。緩解方式是目錄獨立、命名明確，並在後續里程碑的任務中列入刪除項。
