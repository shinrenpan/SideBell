## Context

W1 結束時，App 打開就是一個丟棄式的傳輸驗證畫面：一個角色切換器加幾顆測試按鈕。傳輸層已經過雙實機驗證（背景送達延遲 1 秒、系統終止後復活延遲 0 秒），但沒有任何正式的畫面結構承載它。

本 change 要立起最外圍的三層容器，讓後續每個畫面都有明確的歸屬。三個既有條件框住了設計：

1. **角色設定由照顧者操作，不是患者。** 患者端裝置的初始設定包含選角色、通過系統配對對話框、可能還要關閉自動鎖定——這些在眼控下做不到。現實中是家屬把 iPad 設定好、架在床邊，患者才開始使用。因此首頁的文案與互動都是對照顧者說的。
2. **患者一旦離開呼叫畫面可能回不來。** 這使得患者端的任何導航控制都是風險，而不只是介面選擇。
3. **免責聲明是 App Review 的必做項目**（spec 9.3），屬於會被拒的類別而非加分項。

## Goals / Non-Goals

**Goals:**

- 立起三層容器：首頁、患者端導覽堆疊、照顧者端分頁容器。
- 讓免責聲明進入產品，並具備可佐證的主動確認紀錄。
- 讓已設定過的裝置一開 App 就在崗位上，不再經過任何選擇。
- 集中導航行為，讓後續畫面不需要各自操作導覽控制器。
- 在骨架改動後，W1 已驗證的傳輸行為不退化。

**Non-Goals:**

- 患者端格子畫面、格子編輯、SwiftData 資料模型。
- 照顧者端的呼叫清單、歷史紀錄、警報、本地通知。
- 贊助頁與 RevenueCat。
- 重送／確認狀態機的完整定義。
- 刪除傳輸驗證畫面——正式畫面完成前仍需靠它確認傳輸行為。
- onboarding 教學（不要滑掉 App、引導使用模式、配對步驟）。

## Decisions

### 首頁為根畫面，角色容器以全螢幕呈現而非推入堆疊

角色是一種「模式」，不是導覽層級中的一站。以推入方式進入會讓返回手勢隨時可能把患者滑出呼叫畫面，也會讓返回按鈕出現在患者端的導覽列上——那正是我們最想避免的東西。

首頁不可省略。即使已選過角色而直接進入容器，首頁仍必須實際存在於根，否則「切換角色」時沒有可返回的目標。

替代方案是把角色容器直接設為 window 的根、切換角色時整個換掉根。否決原因是換根沒有轉場語意、狀態管理更亂，而且與既有的導航規範（由 `source.navigationController` 動態取得）衝突。

### 導航集中於 AppRouter，畫面不自行操作導覽控制器

進入角色、離開角色、開啟設定，全部經由導航中樞執行。各 ViewModel 只表達意圖，由 C 層轉交。

這麼做的直接理由是本 change 有三個不同來源會觸發同一種轉場（首頁選擇角色、啟動時自動進入、設定頁切換角色），若各自實作會出現三套略有出入的行為。

### 啟動時依既有角色決定去向，且不帶轉場動畫

場景配置完成後同步檢查角色設定：未選擇則停在首頁；已選擇則立即呈現對應容器，不帶動畫。

不帶動畫是刻意的——使用者不該看到首頁一閃而過，那會讓人以為自己按錯了什麼。對照顧者而言，App 打開的第一眼就該是崗位畫面。

### 免責確認與角色同層儲存

兩者都必須在任何介面建立之前讀到，且都是單一純量值。與角色設定放在同一層輕量儲存，沿用既有的儲存策略，不引入資料庫。

### 藍牙可用性只採信明確狀態，未判定一律放行

只有明確的「已關閉」「未授權」「不支援」才停用角色按鈕。「未判定」與「重設中」放行。

這條規則是必要的而非保守：首次啟動時沒有任何 Bluetooth manager 存在（沒選角色就不會建立），可用性必然讀為未判定。若把它當成不可用，使用者將永遠無法進入——權限對話框要等 manager 建立才會出現，而 manager 要選了角色才會建立。這是一個會鎖死整個 App 的死結。

首頁需要在尚未建立 manager 的情況下觀察藍牙狀態，因此需要一個獨立於傳輸角色的可用性來源。

### 患者端不設分頁列，設定入口採兩步驟確認

患者端的畫面全部給患者內容。設定入口是右上角一顆低調的文字控制項，需要**連續兩次點擊**才會開啟，且兩次之間控制項的外觀與文字會改變；三秒內未完成第二次即自動取消。

原本的設計是「只回應長按」——理由是 Dwell Control 觸發的是單擊、不產生長按，眼控在原理上到不了這個入口。實測證實它確實擋得住眼控，但也擋住了 VoiceOver 使用者：「雙擊並按住」時機難以拿捏，改用無障礙自訂動作亦不穩定。**可達性不等於可用性**——一個要重試好幾次的操作，對每天使用的人就是障礙。

改用兩步驟後，防護不再依賴「某種使用者做不出某個手勢」，而是依賴「連續兩次精準命中、且中間目標會變」。這對所有輔助技術一視同仁：眼控要在三秒內對兩個不同狀態各精準停留一次，機率極低；VoiceOver 與手指使用者則都只是普通的兩次點擊。

進入待確認狀態時須主動朗讀通知——視障使用者看不到文字變化，不通知的話會以為第一次點擊沒有作用。

用文字而非圖示：照顧者一輩子只按幾次，需求是「第一次就找得到」，而圖示要先看懂才知道是什麼。

**入口的所在位置屬於主畫面，不屬於容器。** 它是主畫面 toolbar 上的一個項目，狀態歸該畫面的 ViewModel，導航經由 `onRoute` 交給 C 層。先前的版本把按鈕疊在容器的 view 上，繞過了整個分層：狀態管理落在容器裡、導航直接呼叫導航中樞、按鈕還跟內容搶同一塊畫面空間，實測時 VoiceOver 的聚焦框把它和下方內容框在一起。改用標準 toolbar 的代價是頂部多佔約 44pt，但省下那 44pt 換來架構偏離與無障礙缺陷並不划算。

兩步驟確認本身抽成可重用元件，讓正式的格子畫面取代驗證畫面時可直接沿用，不需重寫。

### 照顧者端為分頁容器，兩個分頁各自持有導覽堆疊

兩個分頁後續都會有子頁（呼叫詳情、設定項目），因此各自需要導覽堆疊。本 change 只建立骨架與「切換角色」，內容留給後續里程碑。

### 角色容器的主畫面暫時沿用傳輸驗證畫面

患者端與照顧者端的主畫面在本 change 仍是 W1 的傳輸驗證畫面。

理由是回歸驗證：骨架改動涉及啟動時序、場景配置、傳輸啟動點，這些正是 W1 花了兩天才驗證通過的區域。保留一個已知可用的畫面，才能在改完之後立刻確認傳輸行為沒有退化。等正式畫面就位再整個目錄刪除。

### 離開角色時停止該角色的傳輸活動

從設定切換角色時，先停止傳輸再返回首頁。

不停止的話，患者端會在使用者以為已經離開的情況下繼續廣播，照顧者端也會繼續掃描——兩者都與畫面呈現的狀態不符。W1 的教訓是：畫面宣稱的能力必須等於實際能力。

### 首頁說明區可捲動，角色按鈕釘在底部

說明區（標題、免責聲明、確認控制項）放在可捲動的區域，角色按鈕固定於底部。

理由是三個變因會疊加：放大的 Dynamic Type、小尺寸螢幕、較長的翻譯（德文、越南文可能比中文長三到五成）。固定版面在三者同時發生時會把文字直接裁掉，而被裁掉的部分使用者永遠看不到——那對一份免責聲明是不能接受的。

確認控制項刻意放在聲明**下方的捲動區內**。使用者為了啟用角色按鈕必須捲到它，因而必然捲過整段聲明——這比把所有內容硬塞進一個畫面更能保證他真的看過。原先的固定版面反而允許使用者完全不看就直接按按鈕。

按鈕釘在底部則保證：不論說明多長、字級多大，按鈕永遠在拇指可及之處，不會被內容推出畫面。

### 無障礙隨畫面實作，不留到後期打磨

首頁的每個互動元素在本 change 就帶上標籤、提示與正確的朗讀順序，不等 W5。

理由是成本結構：隨畫面做幾乎沒有額外成本，最後補做則常常要重寫——自訂控制項讀不到、朗讀順序與視覺順序不一致、狀態變化沒有通知。spec 第 7 節的 W5「無障礙打磨」是實測與調整，前提是前面每一片都已經做過基本功。

這也牽動長按設計的評估：長按對眼控是障礙（那正是我們要的），但對 VoiceOver 使用者必須可達。

實測結果：VoiceOver 的「雙擊並按住」技術上能觸發長按，但時機難以拿捏、需要試好幾次——**可達性不等於可用性**，一個要重試的手勢對每天使用的人就是障礙。因此改為提供無障礙自訂動作，讓 VoiceOver 使用者以標準的動作選擇機制開啟設定。自訂動作只存在於 VoiceOver 情境，眼控使用者碰不到，防誤觸的設計未被削弱。

## Implementation Contract

**行為**：首次啟動看到首頁，畫面上有免責聲明、一個未勾選的確認控制項、兩顆停用中的角色按鈕。勾選後按鈕啟用。選擇角色後全螢幕進入該角色，傳輸以該角色啟動。關閉 App 再打開，直接進入該角色的畫面，不再看到首頁。從設定切換角色，回到首頁且傳輸停止。藍牙關閉時首頁的角色按鈕停用並說明原因，開啟後自動恢復。

**介面形狀**：

- 首頁的狀態包含：免責是否已確認、藍牙可用性、角色按鈕是否可用。
- 導航中樞提供三個操作：進入指定角色、離開目前角色回到首頁、開啟目前角色的設定。
- 免責確認的儲存提供讀取與標記兩個操作，讀取為同步。
- 藍牙可用性的觀察不得要求先選定角色。

**失敗模式**：

- 藍牙不可用：角色按鈕停用並顯示原因，不得靜默停用。
- 免責未確認：角色按鈕停用並顯示原因，與藍牙原因可區分。
- 角色設定讀取到非法值：視為未選擇，停在首頁——猜一個角色比沒有角色危險，患者端會誤以為自己在廣播。
- 場景配置時取不到已建立的核心物件：以斷言暴露，不得靜默降級為空畫面。

**驗收標準**：

- 免責確認儲存的單元測試：預設未確認、標記後為已確認、重建儲存後仍為已確認。
- 藍牙可用性到按鈕狀態的映射，逐列對照 `role-selection` 中的範例表。
- 實機驗收：首次啟動流程、關閉重開直接進入角色、切換角色回首頁、藍牙開關時按鈕狀態變化、患者端單擊設定無反應而長按可進入。
- 回歸驗收：骨架改動後，W1 驗證清單的 V3（呼叫送達與確認閉環）與 V7（鎖屏背景送達）仍通過。
- 無障礙驗收：開啟 VoiceOver 後首頁所有元素可聚焦、朗讀內容說明用途、停用原因可辨、朗讀順序與視覺順序一致。

**範圍界線**：

- 範圍內：首頁、免責確認、藍牙停用邏輯、導航中樞、兩個角色容器骨架、兩端的最小設定（僅切換角色）、啟動去向判斷。
- 範圍外：格子畫面與編輯、呼叫清單與歷史、警報與通知、贊助、資料庫模型、onboarding 教學、傳輸驗證畫面的刪除。

## Risks / Trade-offs

- **首頁需要在沒有傳輸角色的情況下觀察藍牙狀態** → 現有的可用性判斷長在兩個 BLE 端點裡，而端點要選了角色才建立。需要一個獨立的觀察來源；若處理不當會回到「未判定即停用」的死結。實作時須以 `role-selection` 範例表的六列逐一驗證。
- **長按作為患者端設定入口，依賴「Dwell Control 只產生單擊」這個未經親自驗證的前提** → 列入實機驗證清單。若不成立，改為長按加二次確認。
- **啟動時立即呈現容器可能與場景還原時序衝突** → 系統因 BLE 事件在背景啟動 App 時，場景可能根本不會建立。呈現邏輯必須寫在場景配置中而非啟動回呼中，否則會在沒有場景的情況下嘗試呈現。
- **傳輸驗證畫面留在正式骨架裡** → 有隨正式版一起上架的風險。緩解方式是目錄獨立、命名明確，並在患者端格子畫面的 change 中列入刪除任務。
- **免責聲明的措辭尚未定稿** → 本 change 先以 spec 9.3 的語意實作，正式文案須在送審前與 App Store 描述一併檢視，兩者不得出現「緊急醫療警報」的暗示。
