## Context

W3 種下四個預設格子（喝水／翻身／洗手間／不舒服）並明白寫著「格子編輯留給下一片」。此後累積了三條專為它保留的約束（`DECISIONS.md`）：格子數量上限由螢幕決定、捲動只是降級路徑、圖示不做。

編輯功能的操作者是照顧者，但**資料在患者的裝置上**——格子存在患者端的資料庫裡，透過 BLE 傳出的呼叫也由那裡發起。因此編輯畫面必須在患者端的裝置上，經由那個已有兩段確認保護的設定入口進入。`DECISIONS.md` 寫的「照顧者操作的另一個畫面」指的是操作者，不是裝置。

## Goals / Non-Goals

**Goals:**

- 照顧者能把呼叫項目調整成這個家庭真正需要的內容。
- **患者永遠有一個緊急求助管道**，不因任何編輯操作而失去。
- 患者記住的實體位置不被意外打亂。
- 編輯的複雜度不外洩給照顧者：他要填的是名稱，不是概念。

**Non-Goals:**

- 圖示、重複觸發的去重、捲動的降級路徑（見 proposal 的 Non-Goals）。
- 多患者的項目管理、範本庫、編輯歷史與復原。

## Decisions

### `不舒服` 是受保護的項目：可改名、不可刪除、永遠第一格

三種保護各有不同的理由：

- **不可刪除**——它是患者唯一的緊急求助管道。若允許刪光，患者端會變成一片空白，而他沒有能力自己補救。這比「攔阻最後一次刪除」更好：攔阻會讓照顧者撞牆並困惑，永遠保留一格則使那個情境從不發生。
- **永遠第一格**——`DECISIONS.md` 記載「患者記住的是實體位置，順序必須穩定」，而最緊急的那一格最不能移動。它比原本記錄的「緊急格子釘在第一屏」更嚴格：釘在第一個位置。
- **可以改名**——保護的是「永遠有一個緊急求助鍵」，不是那三個字。有些家庭說「不適」、有些說「疼痛」、有些直接叫「快來」。

實作上以資料模型的一個旗標標記，而非以標題文字或位置判斷——**否則改名之後保護就失效了**。

### 首次安裝只種兩個項目

四個是替照顧者假設的需求。「翻身」對能走動的患者無用，「洗手間」對包尿布的患者無用，而真正需要的（換尿布、抽痰）我們一個都沒猜到。

留 `不舒服`（受保護，必要）與 `喝水`（最普遍的日常需求，同時作為「格子長什麼樣」的示範）。其餘由照顧者自己加——這也符合 `DECISIONS.md` 的「患者端一律取簡」：每多一格，患者每次尋找目標的視覺掃描成本都會上升。

### 編輯畫面是清單，不是格子

用格子編輯格子，等於把「觸發呼叫」與「調整設定」兩種操作放在同一種介面裡，照顧者會不確定點下去會發生什麼。

清單是一維的，天然適合排序與刪除，也是 iOS 使用者熟悉的編輯形式。**排序用標準的拖拽**——一維的拖放不會有「拖到哪一格」的歧義，而照顧者有完整的操作能力。

拖拽時 `不舒服` 不可移動，其他項目也不能被拖到它前面。

### 緊急等級不開放設定

只有受保護的 `不舒服` 是緊急呼叫。開放設定會帶來兩個問題：照顧者必須理解「緊急代表警報會重複到有人確認」這件事，而誤設的代價是每天被重複警報疲勞轟炸——警報一旦被當成噪音，真正的緊急就叫不動人了。

代價是需要第二個緊急項目的家庭無法自訂。若日後實際回饋顯示有此需求，再開放不遲；反過來（已開放後要收回）則會破壞既有使用者的設定。

### `commandCode` 由系統產生，不出現在編輯畫面

每則呼叫在 wire format 中帶一個機器可讀的短碼，上限 8 位元組 ASCII。照顧者要填的是「換尿布」，不是想一個八字元的英文代號。

新增項目時自動產生一個唯一短碼即可。它目前的用途是讓照顧者端不必依賴標題文字就能辨識呼叫類型；標題可自訂之後這個價值下降，但保留它不需要成本，而未來的統計功能（「這個月按了幾次翻身」）會用到。

### 數量上限在「新增」那一步擋，並說明原因

`DECISIONS.md` 已定：硬上限是「一屏放得下」（螢幕高度 ÷ 最小格子尺寸 150pt），另建議不超過 6 格（外部無障礙指南以視覺疲勞為由）。

達到上限時**擋下新增並說明「再加就會有格子患者看不到，要不要換掉現有的某一項」**，逼照顧者做取捨——取捨正是這個產品該逼他做的事。靜靜地讓他加完、然後患者默默漏掉，是最糟的結果。

### 編輯結果立即生效，不需要確認或套用

每一次新增、改名、刪除、排序都直接寫入資料庫。患者端的格子畫面在下次出現時讀到新內容。

不做「編輯／完成」的暫存模式：那需要處理「編輯到一半離開怎麼辦」，而照顧者可能在任何時候被患者叫走。立即生效沒有這個問題。

刪除是唯一的例外——它不可復原，因此需要確認對話框。

## Implementation Contract

**Behavior**

- 患者端設定頁出現「編輯呼叫項目」一列，點選後開啟編輯清單。
- 清單依患者端格子的順序呈現所有項目。第一列固定是受保護的項目。
- 照顧者可：新增項目（只填名稱）、修改任一項目的名稱（含受保護的那一項）、刪除非受保護的項目（需確認）、以拖拽調整非受保護項目的順序。
- 受保護的項目：沒有刪除入口、無法被拖動、其他項目無法被拖到它之前。
- 項目數達上限時，新增入口被停用並說明原因。
- 任何變更立即寫入，患者端格子下次呈現時反映新內容。
- 首次安裝種下兩個項目：受保護的 `不舒服` 與可刪除的 `喝水`。

**Interface / data shape**

- `GridItemModel` 新增一個布林欄位標記「受保護」。判斷保護狀態**只依此欄位**，不得依標題文字或 `sortOrder` 推斷。
- `GridItemStore` 新增：新增項目（產生 `commandCode` 與 `sortOrder`）、更新標題、刪除項目、重新排序。刪除受保護項目的請求**必須失敗並回報明確的錯誤**，不得靜默忽略。
- `GridEditingViewModel`：沿用專案既有的 `doAction` 單一進入點，動作包含 `onAppear`、`add(title)`、`rename(id, title)`、`delete(id)`、`move(from, to)`、`dismissFailure`。

**Failure modes**

- 嘗試刪除受保護項目：`GridItemStore` 擲出錯誤。此路徑在 UI 上不可能觸發（沒有入口），但資料層仍須把關——UI 的保護是體驗，資料層的保護才是保證。
- 標題超過 wire format 上限（100 位元組 UTF-8）：新增或改名時即拒絕並說明，不等到患者按下才發現。這條沿用 `grid-storage` 既有的驗證。
- 標題為空白：拒絕，患者無法辨識一個沒有名字的格子。
- 達數量上限仍嘗試新增：新增入口已停用；若仍被呼叫則擲出錯誤。

**Acceptance criteria**

- `Tests/GridEditingTests/GridEditingStateTests.swift` 覆蓋：新增後項目數增加且順序在最後、改名後標題更新、刪除非受保護項目成功、**刪除受保護項目失敗**、受保護項目在排序後仍位於第一、達上限時新增被拒、空白標題被拒、超長標題被拒。
- `Tests/PersistenceTests/GridItemStoreTests.swift` 更新：首次種子產生**兩個**項目，其中一個受保護。
- 以 grep 確認保護狀態的判斷只讀該欄位，未出現以標題文字或索引位置判斷保護的程式碼。
- 實機驗證清單 `docs/device-verification/w7-grid-editing.md` 涵蓋：新增後患者端出現該格、改名後患者端更新、刪除後消失、排序後患者端順序一致、受保護項目無刪除入口且無法拖動、達上限時的說明、以及首次安裝為兩格。

**Scope boundaries**

- 在範圍內：編輯畫面四件套、`GridItemStore` 的增刪改排序、`GridItemModel` 的保護旗標、設定頁入口、種子改為兩項、既有測試與 W3 驗證清單的更新。
- 不在範圍內：患者端格子的觸發行為與版面演算法、圖示、重複觸發去重、捲動降級路徑、照顧者端任何檔案、多患者管理。

## Risks / Trace-offs

- **既有安裝的資料庫沒有「受保護」欄位** → SwiftData 的輕量遷移會為既有資料填入預設值（false），導致舊裝置上沒有任何受保護項目。開發期間以刪除 App 重裝處理；正式發布前若已有真實使用者，需要一次性的資料修正將既有的 `不舒服` 標記為受保護。目前尚未上架，此風險僅存在於開發裝置。
- **改名後受保護項目與其標題脫鉤** → 這是刻意的：保護的是那個位置與它的不可刪除性，不是文字。但照顧者若把它改成「喝水」，畫面上會有兩個相似的名稱而其中一個不能刪。不做額外限制——照顧者有權決定用詞，而混淆的代價由他自己承擔。
- **數量上限依螢幕計算，而患者端與編輯畫面在同一台裝置上** → 上限值可直接由該裝置的螢幕算出，不需跨裝置協調。但若日後支援在照顧者裝置上遠端編輯，上限的計算基準就要重新設計。
- **立即生效沒有復原** → 以刪除的確認對話框防止誤刪。改名與排序的誤操作可以自己改回來，成本低。

## Migration Plan

1. 先改資料層：`GridItemModel` 加保護旗標、`GridItemStore` 加增刪改排序、種子改為兩項，並更新既有測試。
2. 建立編輯畫面四件套與其測試。
3. 接上設定頁入口與轉場。
4. 更新 W3 驗證清單中「四格」的描述。
5. 實機驗證。

回退策略：本片不改動患者端格子的觸發與版面邏輯。若編輯功能出問題，可移除設定頁入口而保留資料層改動，患者端行為不受影響。

- ~~數量上限的建議值（6）與硬上限（一屏放得下）~~ → **已定案（2026-08-13）**：**硬上限 = 一屏放得下**（`maxItemCount(in:)`），**超過建議值 6 只提示、不擋**（`state.isCrowded`）。

  落差比預期的更大：iPad mini 直向一屏塞得下 **24 格**（4 欄 × 6 列），不是原本猜的 8 格。

  中途曾改成 `min(6, 一屏放得下)`，理由是 24 個選項對眼控患者是災難。**那個改法後來被推翻**——它與 `DECISIONS.md` 2026-08-08 的原文矛盾，而該文早就權衡過：6 來自外部無障礙指南、**自承未附實證來源**，因此明訂為「建議而非硬上限」，且「超過 6 格時應**提示**照顧者」。拿一個沒把握的數字硬擋，等於替照顧者決定他家裡需要幾個項目——而他才是知道患者需要什麼的人。

  真正有實證的約束是「緊急呼叫零捲動可達」，那個由一屏上限守住。兩層因此各司其職：硬上限擋的是「患者看不到」，建議值提示的是「找起來更費力」。
