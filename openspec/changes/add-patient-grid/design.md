## Context

這是整個產品最核心的畫面：患者唯一能主動使用的介面，也是他在無法言語、無法移動時唯一的求助管道。其他所有畫面都是為了讓這一頁能運作而存在。

四個既有條件框住了設計：

1. **唯一可用的互動是單擊。** 系統的 Dwell Control 只發出單擊，任何超出單擊的手勢都會讓產品的主要功能對目標使用者失效。
2. **每一次互動都有實質成本。** 眼控需要凝視數秒、單指操作需要體力。因此每個功能都必須先通過「這對患者有行動價值嗎」這一關，沒有的一律不做。
3. **患者可能看不見。** 只存在於畫面上的回饋，對視障患者等於不存在；只靠顏色區分的狀態，對色覺障礙者也不存在。
4. **螢幕不能睡。** 裝置鎖屏後眼球追蹤不運作，患者無法喚醒它——螢幕一暗，整套系統等同離線。

呼叫的重送與逾時規則已於 spec 第 8 節議程第 2 項拍板（事件驅動重送、三分鐘逾時、三種狀態），本設計依其實作。

## Goals / Non-Goals

**Goals:**

- 讓患者用單擊就能求助，並清楚知道有沒有人收到。
- 讓「照顧者暫時離開」不等於呼叫失敗。
- 讓看不見的患者也能確認自己按到了什麼、也能知道有人回應了。
- 讓格子的位置在每次啟動後保持一致，使患者建立的肌肉記憶與注視目標持續有效。

**Non-Goals:**

- 格子編輯（新增、刪除、改文字、排序、緊急等級）——照顧者操作的另一個畫面。
- 照顧者端的呼叫清單、歷史紀錄、警報與通知。
- 緊急呼叫的差異化行為——屬議程第 4 項的警報策略。
- onboarding 教學與贊助頁。
- 刪除傳輸驗證畫面——照顧者端仍需靠它驗證。

## Decisions

### 呼叫狀態機獨立於 Core，不長在 ViewModel 裡

待送佇列、重送觸發、逾時判定全部放在核心層的一個型別，ViewModel 只讀它的狀態。

理由是這套規則與畫面無關：照顧者端未來也會消費同一組狀態（例如顯示「患者的呼叫尚未確認」）。把它寫進 ViewModel 等於綁死在患者端的生命週期上，而 ViewModel 隨畫面生滅——那正是 W1 已經踩過的坑（事件消費者一度綁在畫面上，App 於背景被喚醒時沒有人接）。

### 重送以連線事件觸發，不做定時輪詢

送不出去的呼叫進入待送佇列，於傳輸層回報「已連線」時立即送出。

不用定時輪詢的理由有二：延遲（照顧者回來後最多要等一個完整週期才會送出）與耗電。傳輸層本來就會回報連線變化，事件已經在那裡。這也與 spec 3.1 已定的「不自行輪詢，靠系統事件」一致。

### 逾時的計時起點是患者按下，不是送出

三分鐘從患者觸發的那一刻起算，無論呼叫是否曾經成功送出。

理由是這個數字衡量的是**患者等了多久**，不是技術上重試了多久。若從送出起算，一則排隊兩分鐘才送出的呼叫會讓患者總共等上五分鐘——而他不知道其中兩分鐘是排隊。

### 呼叫狀態只存在記憶體，格子項目才進資料庫

格子項目（標題、順序）存入本地資料庫；呼叫狀態不存。

App 重啟後復活的舊呼叫是假警報而非遲到的訊息——它描述的需求通常已經過去，而假警報會侵蝕照顧者對警示的信任。這條與 W1 已定的「未確認呼叫不持久化」是同一個決策的延伸。

### 預設格子以是否種過為判準，不以是否為空

首次使用時寫入四個預設格子，並記錄已完成種子。之後即使格子被清空也不再重新種。

以「空即種」為判準會讓「照顧者刻意清空格子」變成不可能——每次啟動都會被塞回四個預設項目。

### 格子欄數依可用寬度自適應，不寫死

欄數由實際寬度決定，並保證每格不小於規格要求的尺寸。

寫死欄數會在手機直向產生窄到無法用眼控命中的格子，在平板上又浪費空間。而本產品同時支援兩者。

### 狀態以符號與文字表達，顏色只是輔助

三種狀態各自帶有不同的符號，並在 VoiceOver 中朗讀，顏色僅作強化。

只靠顏色會排除色覺障礙者；只存在於畫面的狀態對視障患者等於不存在。

### 確認到達時發出震動與音效，不只更新畫面

確認是患者唯一的安心來源。畫面上的打勾對看不見的患者不存在，而視力不便的患者也可能剛好沒在看。失敗的回饋須與確認的回饋明顯不同，避免兩種結果被混淆。

### 語音播報只播最新一則，不排隊

連續觸發多格時，新的播報取代舊的，不依序播完。

排隊播報會讓患者在誤觸數次後聽到一長串無關的內容，而他最需要確認的是「我剛剛按到的是什麼」。

### 防休眠在患者容器的顯示與消失時切換

進入患者畫面時停用自動鎖定，離開角色時恢復。

放在容器而非畫面，是因為未來患者端會有多個畫面（例如格子編輯），防休眠應涵蓋整段停留期間；而恢復必須確實發生——照顧者端的手機不能跟著一起不睡。

## Implementation Contract

**行為**：患者看到一整片大格子與常駐的連線指示。點一下任一格，裝置唸出該格的名稱，格子顯示「等待中」。照顧者確認後，格子轉為已確認並伴隨震動或音效。若照顧者不在範圍，呼叫留在等待中，並在他回來的瞬間自動送出。從按下起算三分鐘內沒有回應，格子轉為「無人回應」。畫面停留期間裝置不會自動鎖定。

**介面形狀**：

- 呼叫生命週期由核心層一個型別管理，對外提供：送出一則呼叫、觀察每則呼叫的狀態、以及依格子識別碼查詢最近一次呼叫的狀態。
- 呼叫狀態為三值：等待中、已確認、無人回應。
- 格子儲存提供：讀取全部項目（依順序）、寫入項目、首次種子。
- 語音播報提供單一操作：播報一段文字，取代進行中的播報。
- 回饋提供兩個操作：確認到達、呼叫失敗，各自對應不同的震動與音效。

**失敗模式**：

- 傳輸層回報未連線：**不視為失敗**，轉為待送。
- 傳輸層回報編碼失敗或角色錯誤：視為立即失敗，該呼叫直接進入「無人回應」——這類錯誤重試不會好轉。
- 格子項目超出 wire format 限制：於**儲存時**拒絕並說明限制，不留到送出時才失敗。
- 資料庫載入失敗：以斷言暴露，不得靜默降為空白格子——一片空白的格子對患者而言是「我的求助按鈕全部消失了」。

**驗收標準**：

- 呼叫狀態機的單元測試涵蓋 `call-delivery` 範例表的四種組合，含逾時、逾時後才到達的確認、連線恢復時的批次送出。
- 格子儲存的單元測試涵蓋 `grid-storage` 範例表的五種驗證情形，以及「刻意清空後不重新種子」。
- 實機驗收：單擊送出、語音播報、確認的震動回饋、離開範圍後回來自動送出、三分鐘逾時、螢幕不自動鎖定、VoiceOver 朗讀格子與狀態。
- 版面驗收：iPhone 直向與 iPad 橫向的欄數不同，且兩者每格皆不小於規格尺寸。

**範圍界線**：

- 範圍內：格子畫面與其狀態、呼叫生命週期、格子儲存與預設種子、語音播報、確認回饋、連線指示、防休眠。
- 範圍外：格子編輯、照顧者端任何畫面、警報策略、onboarding、贊助、傳輸驗證畫面的刪除。

## Risks / Trade-offs

- **三分鐘的計時依賴 App 持續執行** → 患者端畫面保持前景且螢幕不睡，因此成立；但若患者端被系統終止，計時隨之消失。這與「狀態不持久化」的決定一致，不另做補償。
- **語音播報與未來的警報共用音訊資源** → 患者端目前只有播報、照顧者端才有警報，兩者在不同裝置上，暫無衝突。但若日後患者端加入音效提示，須一併檢視音訊工作階段的設定。
- **預設格子的用詞可能不適合所有家庭** → 「喝水／翻身／洗手間／不舒服」取自 spec，但實際需求因人而異。這正是格子編輯必須緊接在後的原因，兩片之間不宜間隔太久。
- **格子數量增加後版面會退化** → 本片只保證四格的呈現；當照顧者新增到十格以上時，自適應欄數會讓每格縮小到規格尺寸以下。屆時需要捲動或分頁，屬格子編輯那一片要一併處理的問題。
- **震動在 iPad 上不存在** → iPad 沒有震動硬體，確認回饋在患者端（多為 iPad）只能靠音效。因此音效不可省略，不能把震動當成主要通道。
