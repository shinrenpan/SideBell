## Context

SideBell 到目前為止是一個**完全離線、零第三方依賴**的 App：BLE 直連、資料不出裝置、`project.yml` 裡沒有任何套件。W1 的決策明文寫著「不引入任何第三方 Swift 套件」。

贊助功能同時打破這兩件事：它需要網路，也需要 RevenueCat SDK。因此本片的設計重點不是「怎麼賣東西」——那是 SDK 的職責——而是**如何把這個例外圈在最小的範圍內**，讓 App 的其餘部分維持原本的性質。

另有一項既有約束：贊助入口只能出現在照顧者端。患者端是眼控操作的介面，購買流程在那裡不只是誤觸風險，更是把金錢決策放在一個沒有能力承擔它的使用者面前。

## Goals / Non-Goals

**Goals:**

- 滿足 Shipaton「以 RevenueCat SDK 驅動至少一項 IAP」的參賽要求。
- 讓願意支持的使用者有明確的管道，且知道自己的錢會變成什麼。
- **購買不影響任何功能**，且這件事在程式結構上就成立，不只是文案宣稱。
- 網路與第三方依賴的影響侷限在贊助頁，其餘畫面完全不受影響。

**Non-Goals:**

- 社福機構的捐款連結清單（與離線定位衝突，比賽後再議）。
- 公開的捐贈比例承諾。
- 恢復購買、訂閱、買斷、entitlement gating。
- 贊助者的 app icon 變體（`[v1.1]`）。

## Decisions

### 不存在「已解鎖」的概念，程式裡沒有可判斷的旗標

App 內**不得出現任何形如「是否已贊助 → 給予某功能」的判斷**。這不是文案上的保證，而是結構上的：沒有 entitlement 查詢、沒有功能開關、沒有付費牆。

這條約束帶來一個附帶好處：spec 第 5 節指出訂閱制的死角是「長期斷網時憑證無法驗證，對臥床患者是災難場景」。既然沒有任何功能依賴購買狀態，那個死角在結構上就不存在。

唯一與購買狀態有關的是設定頁的感謝徽章，而它是純裝飾。

### 感謝徽章只記在本機，不向 RevenueCat 查詢

購買成功後在本機記錄一個布林值，與角色設定同層儲存。設定頁據此顯示徽章。

不用 RevenueCat 的購買歷史查詢，理由是離線：照顧者可能長期不連網，而向伺服器查詢會讓徽章在離線時消失——使用者付了錢卻看不到感謝，比不顯示徽章更糟。

代價是換裝置後徽章不會跟著走。可以接受：它是裝飾，不是資產。

### 商品清單寫死在程式裡，不從遠端取得

三個商品識別碼（`com.shinrenpan.sidebell.tip.small`、`…medium`、`…large`）以列舉定義於程式內，價格與在地化名稱則由 App Store 提供（RevenueCat 代為取得）。

識別碼是**含 bundle ID 前綴的完整 product ID**，不是簡短的 `tip.small`。`Purchases.products(_:)` 收的是 App Store 的 product ID，前綴漏掉時 SDK 回傳空陣列，畫面會呈現「需要網路連線」——一個完全指不到真正原因的錯誤。這條路徑沒有任何自動測試能攔住（單元測試以假 store 驅動，不碰真實識別碼），只有真機或 Test Store 才會現形。

不做遠端設定的商品清單：那需要一個後端，而本 App 沒有、也不打算有。商品變動時重新送審是可接受的成本——它們不會常變。

### 贊助頁是唯一需要網路的畫面，且失敗要說清楚

商品資訊必須向 App Store 取得，因此贊助頁在無網路時無法呈現價格。此時**明確說明「需要網路連線才能載入支持方案」並提供重試**，不假裝正在載入、也不顯示空白。

這條與全 App 的原則一致：畫面宣稱的能力必須等於實際能力。而它的影響侷限在此頁——**其餘任何畫面都不得因為網路狀態而改變行為**。

### 購買失敗分成「使用者取消」與「其他錯誤」

使用者主動取消**不顯示任何錯誤**——那是他的決定，跳出錯誤訊息像是在責備他。其他失敗（付款方式問題、商店不可用）則明確告知並可重試。

這個區分在 RevenueCat 的錯誤型別中可直接取得。

### RevenueCat SDK 的初始化在 App 啟動時完成，但不阻塞任何路徑

SDK 於 `didFinishLaunching` 設定 API key，此步驟不涉及網路請求。商品載入延後到贊助頁出現時才進行——照顧者可能永遠不開那一頁，沒有理由為此在啟動時發出網路請求。

## Implementation Contract

**Behavior**

- 照顧者端設定分頁出現「支持開發者」入口；患者端的設定畫面**沒有**這個入口。
- 贊助頁列出三個支持方案，每項顯示 App Store 提供的在地化**名稱、用途說明與價格**。三者都來自商店，程式裡不寫任何一句方案文案。
- 點選任一方案後進入系統的購買流程。成功後顯示感謝，並在設定頁出現感謝徽章。
- 同一方案**可重複購買**，每次都是獨立的支持。
- 無網路時，贊助頁說明需要網路並提供重試；其餘畫面不受影響。
- 使用者取消購買時不顯示錯誤；其他失敗顯示原因並可重試。

**Interface / data shape**

- `SponsorshipProduct`：三個支持方案的識別碼，以列舉定義。**只有識別碼**——名稱、用途說明、價格都不寫死在程式裡，全部由 App Store 提供。
- `SponsorshipStore`：對外提供「載入方案」「購買某方案」「是否曾經支持過」三個操作。RevenueCat 的型別**不得洩漏到這個型別之外**——View 與 ViewModel 只認識本專案自己的型別，日後若更換金流方案，改動侷限於此。
- `SponsorshipViewModel`：沿用專案既有的 `doAction` 單一進入點，動作包含 `onAppear`、`purchase(id)`、`retry`、`dismissFailure`。

**Failure modes**

- 商品載入失敗（無網路、商店不可用）：頁面顯示需要網路的說明與重試按鈕，不顯示空的方案清單。
- 購買失敗且原因是使用者取消：靜默返回，不留下任何錯誤痕跡。
- 購買失敗且原因是其他：顯示可理解的說明並可重試，不顯示 SDK 的原始錯誤碼。
- 購買成功但本機記錄寫入失敗：徽章不顯示，但購買本身已完成。此路徑不重試、不提示——那筆交易在 App Store 已經成立，而徽章只是裝飾。

**Acceptance criteria**

- `Tests/SponsorshipTests/SponsorshipStateTests.swift` 覆蓋：載入成功後三個方案皆呈現、載入失敗時呈現重試而非空清單、使用者取消不產生錯誤訊息、其他失敗產生可讀訊息、購買成功後標記為已支持。以注入的假 store 驅動，不接觸真實金流。
- 以 grep 確認全專案**不存在**依購買狀態決定功能可用性的判斷，且 `Sources/Features/PatientGrid/` 與 `Sources/Features/PatientHome/` 不含任何贊助相關識別字。
- 以 grep 確認 RevenueCat 的型別只出現在 `Sources/Core/Sponsorship/`。
- 實機驗證清單 `docs/device-verification/w6-sponsorship.md` 涵蓋：沙盒帳號的購買流程、重複購買、取消購買、無網路時的呈現、患者端無入口、以及購買後功能完全不變。

**Scope boundaries**

- 在範圍內：贊助頁四件套、`SponsorshipStore`、設定頁入口與徽章、RevenueCat SDK 的引入與初始化、App Store Connect 的商品建立。
- 不在範圍內：患者端任何檔案、社福機構清單、捐贈承諾、恢復購買、訂閱與買斷、icon 變體、收入分析。

## Risks / Trade-offs

- **App Store Connect 的前置作業有等待時間**（稅務表單、銀行資訊、商品審核）→ 這些與程式無關且可並行，應在實作開始時就送出，不要等程式寫完。這是本片最可能卡住的地方，而它卡住的原因不在程式碼裡。
- **沙盒環境的購買測試容易誤判** → 沙盒帳號的行為與正式環境不同（例如訂閱週期加速、偶發的驗證延遲）。驗證清單需註明使用沙盒帳號，且「購買成功」的判準以 App 內的徽章出現為準，不以沙盒的收據內容為準。
- **第一個第三方依賴** → 引入 SDK 後，建置時間與 App 體積都會增加，且未來的 Xcode/Swift 版本升級多一個相依對象。以「型別不洩漏出 `Sources/Core/Sponsorship/`」的約束把影響圈住，日後要移除或更換時改動範圍明確。
- **贊助頁需要網路，而 App 的定位是離線** → 這個矛盾無法消除，只能侷限。設計上確保其餘畫面完全不查詢網路狀態，且贊助頁的失敗不影響任何呼叫相關的功能。

## Migration Plan

1. 先在 App Store Connect 完成稅務與銀行資訊，建立三個消耗性商品（與程式並行，這步有等待時間）。
2. 引入 RevenueCat SDK，完成初始化。
3. 建立 `SponsorshipStore` 與其測試，以假 store 驅動，此時不接觸真實金流。
4. 建立贊助頁四件套與設定頁入口。
5. 以沙盒帳號完成實機驗證。

回退策略：本片不改動任何既有功能的行為。若 IAP 審核未通過或時程不及，可移除設定頁入口而保留其餘程式碼，App 的所有功能不受影響——這正是「購買不影響任何功能」這條約束帶來的好處。
